# MVP规划与排期

## 1. MVP定义与核心假设

芸析智农第一版MVP的目标不是搭建完整农业平台，而是用最小成本验证一条可运行、可测量的核心链路：**终端采集环境数据—4G上传OneNet—鸿蒙应用展示—用户拍照或语音提问—AI生成建议—用户确认并反馈。**

### MVP边界

**必须完成：**基础传感器稳定采集、设备联网与数据展示、图片/文字/语音输入、端侧基础识别、环境数据融合、解释性建议、异常提醒及人工复核入口。手机端负责现场操作，PC端完成基础监控与任务流转。

**暂不纳入：**大规模多租户管理、复杂计费体系、全作物知识覆盖、专家实时视频问诊、自动控制灌溉施肥设备，以及面向公众的完整供应链溯源平台。上述能力会显著扩大工程范围，但不会直接提升首轮核心假设的验证效率。

### 核心业务假设

1. 农户愿意通过拍照或语音描述问题，而非学习复杂的专业表单。
2. 图像、环境数据与知识库融合后，诊断结果比单一图像识别更具可信度。
3. 用户需要的不是病害名称，而是带时间、步骤和注意事项的每日行动建议。
4. 当系统展示依据、置信度和人工复核入口时，用户更愿意采纳AI建议并提交反馈。

## 2. 核心功能拆解

| 优先级 | 功能范围 | 纳入理由 |
| --- | --- | --- |
| **Must-have** | DHT11/BH1750/DS18B20数据采集；4G与OneNet传输；手机端数据展示；拍照与文字输入；端侧Qwen识别；基础建议；失败重试 | 构成可演示、可验证的最小业务闭环，缺失任一环节都无法验证产品价值 |
| **Should-have** | SpeechKit语音输入、TTS播报、每日计划生成、NotificationKit提醒、PC端工单流转、低置信度云端复核 | 明显降低田间使用门槛，并增强建议的可执行性 |
| **Could-have** | 服务卡片、适宜植物推荐、案例库、生产记录安全存证、消费者扫码溯源展示 | 有助于增强体验和商业叙事，但不影响首轮核心验证 |
| **Won't-have** | 专家实时视频问诊、自动农机控制、复杂ERP、多区域规模化运维、全品类病害覆盖 | 成本和风险过高，待试点证明需求后再投入 |

## 3. 敏捷迭代与联调排期

以**8周、4个Sprint**推进，每个阶段设置可验收交付物，7名成员按算法、鸿蒙前端、后端、硬件和测试/市场职责协同。

| 阶段 | 周期 | 重点任务 | 交付物与验收门槛 |
| --- | --- | --- | --- |
| Sprint 1：硬件可用 | 第1—2周 | 完成电路打样、焊接、传感器标定、4G模块调试，统一设备与字段编号 | 三类传感器可连续采集；异常值可识别；设备断电重启后恢复上报 |
| Sprint 2：数据链路打通 | 第3—4周 | 后端接入OneNet，完成设备鉴权、数据解析、存储和接口；App展示实时与历史数据 | 终端—OneNet—后端—App链路跑通；离线、重复数据和超时状态可追踪 |
| Sprint 3：AI与多端联调 | 第5—6周 | 部署Qwen2.5-VL-3B，接入图片、语音和环境数据；联调鸿蒙手机端、PC端及SSE回传 | 完成一次端侧诊断；推理时延不高于1.23秒；工单可跨设备流转 |
| Sprint 4：校内验证 | 第7—8周 | 开展不少于3批场景测试，记录任务成功、误操作、延迟和用户反馈，修复高优问题 | 全流程可重复演示；关键问题闭环率不低于90%；形成测试报告与下一轮Backlog |

每个Sprint结束进行一次评审与复盘：只验收可运行成果，不以“代码已完成”替代真实链路验证。跨模块问题由一名项目负责人统一维护风险清单，避免硬件、后端和模型分别完成但整体不可用。

## 4. 验证指标与退出机制

| 验证维度 | MVP成功标准 |
| --- | --- |
| 链路稳定性 | 设备采集、上传、展示和诊断任务完成率≥98%，连续演示无阻断 |
| AI能力 | 域内病害识别准确率≥96.0%，端侧推理时延≤1.23秒 |
| 交互质量 | 关键任务误操作率≤1.3%，用户能够独立完成拍照/语音提问与结果查看 |
| 闭环质量 | 建议可转为计划并提交反馈；≥3批校内测试，关键问题闭环率≥90% |
| 安全边界 | 低置信度结果能够触发复核，不直接输出高风险确定性结论 |

### 退出与调整规则

- **Persevere（继续）**：核心指标达标且用户能够理解、执行建议，进入第二年试点准备，扩展至不少于5类作物与2个真实场景。
- **Pivot（调整）**：识别准确但建议采纳低，优先调整解释、计划和提醒；硬件不稳定则缩减传感器种类或引入成熟模块；弱网导致失败则强化本地缓存与离线任务。
- **Hold（暂缓）**：若连续两轮仍无法达到链路稳定性或安全底线，暂停新增功能，回到数据质量、设备可靠性和人工复核机制，避免用功能堆叠掩盖核心问题。
